# 10 · 主流方案与选型对比

选型不是选「最好的」，是选**「你的团队养得起、业务等得及」的那一套**。

::: tip 全章一句话
四条路线，本质是三种取舍：**自己养（可控但贵）、平台养（快但被绑）、生态养（丰富但不可控）**。
:::

## 00 选型决策树 {#overview}

<Diagram id="selection" />

```text
你有专职平台团队吗？
├─ 没有 → 用平台自带市场（Dify / FastGPT / 云厂商）
└─ 有 ── 你服务的对象是谁？
        ├─ 只有内部几个团队 → 纯 MCP + 轻量网关注册（最快）
        ├─ 多部门 + 有合规要求 → 自研轻量 Hub（本书路线）
        └─ 要对外做生态 → 自研 Hub + 市场层（最难，最后做）
```

## 01 纯 MCP 生态方案 {#mcp}

<Source href="https://modelcontextprotocol.io/" org="MCP" label="官方：SDK 与示例 Server" />
<Source href="https://github.com/modelcontextprotocol/registry" org="MCP" label="Registry：服务发现" />

**形态**：直接用 MCP Server + 客户端配置，或接社区公共 MCP 目录。

| 优点 | 缺点 |
| --- | --- |
| 上手最快，一天能跑通 | 没有租户、配额、计费 |
| 客户端生态广（IDE、桌面端都支持） | 每个客户端各配一份，无法集中管控 |
| 协议标准，跨厂商 | 没有版本灰度，升级靠人盯 |

**适合**：内部 3~5 个团队、技能 < 30 个、没有对外收费需求。

::: warning 纯 MCP 的天花板在哪
当出现「A 部门不该看到 B 部门的技能」「要按调用量收费」「要能审计谁调了退款」这三个需求中的任何一个，纯 MCP 就到顶了。**这不是 MCP 的缺陷，是它本来就不管这层。**
:::

## 02 Agent 平台自带市场 {#platform}

<Source href="https://docs.dify.ai/" org="Dify" label="工具与插件市场" />
<Source href="https://marketplace.dify.ai/" org="Dify" label="插件市场（分发形态参考）" />
<Source href="https://doc.fastgpt.in/" org="FastGPT" label="技能库与工作流" />
<Source href="https://docs.langflow.org/" org="LangFlow" label="组件与可视化编排" />

**形态**：用 Dify / FastGPT / LangFlow 这类平台，直接用它的工具/插件体系。

| 优点 | 缺点 |
| --- | --- |
| 一周能上线，可视化配置 | 元数据模型受平台限制 |
| 自带鉴权、日志、工作流 | 多租户与计费能力看版本 |
| 社区插件多 | 深度定制要改源码，升级会痛 |

**适合**：业务先跑起来、平台团队薄弱、需求还没定型。

::: tip 借平台「过渡」的正确姿势
先用平台验证价值，同时把**技能清单按本书的规范写在自己仓库里**。将来迁移到自研 Hub，清单可以直接导入——这是最便宜的可迁移性保险。
:::

## 03 自研轻量底座 {#diy}

<Source href="https://platform.openai.com/docs/actions" org="OpenAI" label="OpenAPI 作为技能描述来源" />

**形态**：API 网关 + 元数据库 + 策略引擎 + 日志，最小可用约 3 个服务。

```text
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  gateway     │   │  registry    │   │  executor    │
│  鉴权/限流   │──▶│  元数据/版本 │──▶│  转发/沙箱   │
└──────────────┘   └──────────────┘   └──────────────┘
        │                  │                  │
        └──────────┬───────┴──────────────────┘
                   ▼
        Postgres（元数据 + 日志分区表）
```

最小实现清单（三周可跑通）：

| 组件 | 最小做法 | 别做什么 |
| --- | --- | --- |
| 网关 | 现成的（Kong / APISIX / Envoy） | 别自己写 HTTP 代理 |
| 注册 | Postgres 两张表（skills / versions） | 别上服务网格 |
| 鉴权 | JWT + scope 表 | 别自研加密 |
| 执行 | 一个异步 worker + 超时 | 别一开始就做沙箱 |
| 日志 | 分区表 + 定时归档 | 别直接进 ES（贵） |

::: danger 自研最容易失控的地方
不是技术，是**范围**。一开始想做「技能市场 + 计费 + 沙箱 + 推荐」，结果半年没上线。**先做能收钱、能控权的最小闭环。**
:::

## 04 云厂商方案 {#cloud}

<Source href="https://help.aliyun.com/" org="阿里云" label="函数计算、API 网关、鉴权体系" />
<Source href="https://cloud.tencent.com/document/" org="腾讯云" label="云函数、API 网关、密钥管理" />

**形态**：用云上的 API 网关 + 函数计算 + 密钥管理 + 日志服务拼一套。

| 优点 | 缺点 |
| --- | --- |
| 免运维，弹性好 | 厂商绑定，迁移成本高 |
| 天然支持 VPC、审计、密钥 | 计费模型复杂，容易超预算 |
| 合规资质齐全 | 冷启动与并发限制要实测 |

**适合**：已有云基础设施、合规要求高、不想养运维团队。

::: warning 云方案的隐藏成本
函数冷启动、跨区流量、日志存储三处最容易超预算。**上线前用真实流量压一遍，别用控制台的示例数据估算。**
:::

## 05 完整选型对照表 {#matrix}

| 维度 | 纯 MCP | 平台自带 | 自研底座 | 云厂商 |
| --- | --- | --- | --- | --- |
| 首次可用时间 | 1 天 | 1 周 | 3~6 周 | 2~4 周 |
| 元数据可控性 | 低 | 中 | 高 | 中高 |
| 多租户 | 无 | 视版本 | 可做 | 可做（要设计） |
| 计费与配额 | 无 | 部分 | 可做 | 可做 |
| 沙箱能力 | 无 | 无 | 可做 | 强（函数/容器） |
| 运维负担 | 低 | 低 | 高 | 中 |
| 迁移成本 | 低 | 高 | 低（自持数据） | 高 |
| 生态丰富度 | 中 | 高 | 低（要自己攒） | 中 |
| 三年总成本 | 低 | 中 | 高（人力） | 中高 |

::: tip 怎么读这张表
**首次可用时间**最短的，**元数据可控性**通常最低。这不是巧合：平台帮你省的时间，是拿控制权换的。问题是：你现在需要控制权吗？
:::

## 06 中小企业最小推荐 {#smb}

如果你只有 1~3 个工程师，且不想半年后才上线：

```text
第 1~2 周   平台（Dify / FastGPT）+ 规范化清单（按第 03 章）
第 3~4 周   把高频技能改为 MCP Server，用官方 SDK
第 5~6 周   加一层薄网关（现成 API 网关）做鉴权 + 限流 + 日志
第 7~8 周   技能清单进 Git，CI 跑 schema 校验 + 评测集
之后        按需补计费与租户（< 20 个租户时，先按团队手工分摊）
```

**不建议做的事**（这个规模下）：

| 别做 | 原因 |
| --- | --- |
| 自研沙箱 | 托管沙箱更便宜也更安全 |
| 自研向量检索 | 用现成数据库的向量能力 |
| 一开始就做多租户 | 先按团队做逻辑隔离，租户数量上来再重构 |
| 做技能市场 UI | 一个 Markdown 目录页就够用 |

::: tip 人话翻译
小团队的正确姿势是「**先把能力管起来，再把平台做漂亮**」。反过来，你在给一个还没人用的平台写登录页。
:::
